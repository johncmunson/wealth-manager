## Current project operating model

This repository uses one dedicated Neon test endpoint for all database-backed test layers. Database-backed commands are local-only and are expected to run one at a time; integration and E2E commands are not designed to overlap with another database-backed command in a separate terminal or on another machine. A command may recreate the shared test endpoint's application schemas before applying migrations and running its suite.

Within a prepared suite, tests should still use unique records and targeted cleanup so ordinary test-file parallelism is safe. Per-run or per-worker databases/schemas are **not** a current requirement. Introduce resource locking or isolated targets only if the project later adds CI, sharding, concurrent developers sharing the endpoint, or an explicit requirement to run database-backed commands concurrently.

In this document, a "test-owned" resource means infrastructure dedicated exclusively to automated tests and validated as the exact test endpoint. It does not imply that every invocation must provision a unique database or schema. The matrix below describes target-state guidance as suites mature; examples such as authenticated E2E journeys are not all acceptance criteria for the initial testing scaffold.

## Setup and teardown lifecycle

Prefer the narrowest lifecycle that provides isolation: immutable configuration at project startup, shared infrastructure prepared once per command, and mutable test data scoped per test. Every cleanup operation must be idempotent and must verify that it targets the dedicated test endpoint. The shared endpoint is command-scoped operationally, not provisioned anew for each run.

| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Unit / server**              | Load only test-safe environment values and install deterministic process defaults such as a fixed timezone when needed. No database, server, or DOM should start.                                                                                                                                                               | Create fresh collaborators and fixtures in `beforeEach` or directly in each test. Reset fake clocks, spies, stubbed globals, and environment changes after each test. Prefer constructing a new subject over resetting shared mutable instances.                                                                                                                                                                   | Normally none beyond restoring process-level state changed by the suite. A unit project should exit without open handles.                                                      |
| **Component**                  | In the component project’s setup file, register jest-dom matchers and configure React Testing Library. After each test, unmount/clean up the React tree, reset MSW handlers, restore mocks and browser-API shims, and return fake timers to real timers. | **Browser component**          | Start the Vitest Browser Mode provider and any browser-compatible MSW worker once at the appropriate project/worker scope. ### Shared Vitest setup

The setup that applies to every Vitest project should remain deliberately small and runtime-neutral because it executes for Node, jsdom, and real-browser layers. Separate Vitest concepts by scope:

- Use Vitest `globalSetup` only for run/project-wide orchestration that can communicate through environment variables or `provide`/`inject`, such as assigning a run ID or validating common test configuration. In a multi-project configuration, a shared global-setup module may execute for each project, so its work must be idempotent and must not assume it is a process-wide singleton. Its teardown should release only resources it created. Code and globals installed there do not automatically become part of each test worker’s runtime.
- Use a shared `setupFiles` entry only for lightweight, runtime-portable test policy, such as a consistent after-test policy for restoring spies, fake timers, stubbed globals, and stubbed environment variables. Put Node-specific environment guards in Node project setup rather than assuming `process` exists in Browser Mode. Set fundamentals such as `TZ=UTC` before Vitest launches so they take effect before application imports and remain consistent across projects.
- Prefer Vitest configuration such as `restoreMocks`, `unstubGlobals`, and `unstubEnvs` where it expresses the policy more reliably than custom hooks. Enable automatic behavior knowingly: blanket `mockReset` can erase intentional mock implementations, while `clearMocks` only clears call history.
- Keep layer-specific setup in each Vitest project: jest-dom and React Testing Library cleanup belong to component tests; browser providers and browser MSW belong to browser-component tests; database creation/migrations belong to database and route integration projects.
- The shared setup must not import `jsdom`, React Testing Library, server-only database modules, browser-only APIs, or application modules that read layer-specific environment variables at import time. It must not connect to PostgreSQL, start MSW, run migrations, seed data, or start Next.js.
- Do not use a global teardown as a substitute for per-test isolation. It is a final resource boundary and interruption fallback, not the first time mutable state should be cleaned.

## Parallelism

Start with Vitest’s defaults: let it parallelize test files within one prepared command, keep tests within a file sequential, and avoid tuning pools or worker counts without measured need. Database-backed tests must use unique records and targeted cleanup under this model. This does not authorize overlapping separate integration/E2E commands against the shared endpoint. If the project later needs command-level concurrency, add locking or isolated targets first. E2E follows Playwright’s worker model rather than Vitest’s.

| Layer                          | Pragmatic ways to scale                                                                                                                                                                        | Main risks and mitigations                                                                                                                                                                                                                   |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Unit / server**              | Increase Vitest workers or shard the suite in CI. Mark only small, demonstrably pure groups as concurrent.                                                                                     | Shared globals, fake timers, environment mutation, and module-level singletons can race. Prefer dependency injection and per-test state; keep tests that mutate process state sequential.                                                    |
| **Component**                  | Rely on file-level parallelism first; shard when the suite becomes large. Increase workers only while memory remains stable.                                                                   | Concurrent tests in one jsdom worker can interfere through the document, timers, and MSW handlers. Use fresh renders and cleanup, local handlers, and generally avoid in-file concurrency.                                                   |
| **Browser component**          | Add browser instances/workers gradually or shard files across CI jobs, usually with Chromium first.                                                                                            | Browsers are CPU- and memory-heavy; shared storage, cookies, ports, and request handlers can leak. Use isolated contexts/pages and unique resources, and cap workers based on CI capacity.                                                   |
| **Database integration**       | File-level parallelism within one command is acceptable when every test uses unique records and targeted cleanup. Do not overlap commands that recreate or migrate the shared schemas.         | Shared rows and broad cleanup cause flakes. Keep fixtures uniquely identified. Add a database lock or isolated schemas/databases before introducing CI sharding or concurrent command execution.                                             |
| **Route / server integration** | Follow the same shared-endpoint rules as database tests. Give any started servers unique ports and namespace users and sessions.                                                               | Database collisions, singleton auth/cache state, port conflicts, and shared remote-service fakes can race. Keep cleanup targeted; add stronger isolation only when actual concurrency requirements demand it.                                |
| **E2E**                        | Increase Playwright workers within one command gradually while retaining fresh browser contexts and unique data. Before introducing CI sharding, define a locking or isolated-target strategy. | Shared accounts, database records, rate limits, server capacity, and order-dependent flows are common bottlenecks. Use worker-scoped identities, deterministic setup APIs, and lower worker counts for constrained or stateful environments. |

## Suggested project separation

## Cross-cutting safeguards

| Concern                     | Recommended approach                                                                                                                                                                                                                                                                                            |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Database safety**         | Validate both database URLs against the exact allowlisted test endpoint before any connection, migration, schema recreation, or cleanup. Neon database names alone do not identify the environment.                                                                                                             |
| **Parallel isolation**      | The current local workflow shares one validated test endpoint and relies on unique records, targeted cleanup, and non-overlapping database-backed commands. Require locks or isolated databases/schemas only before adding command-level concurrency, CI sharding, or multiple developers sharing the endpoint. |
| **Migrations**              | Modify `db/schema/`, generate migrations with `pnpm db:generate`, and apply those generated migrations to test databases.                                                                                                                                                                                       |
| **Environment variables**   | Keep test credentials separate. Remember that E2E may run Next.js with `NODE_ENV=production`; select the test database through explicit environment configuration rather than relying solely on `NODE_ENV=test`.                                                                                                |
| **External services**       | Unit and integration tests should use deterministic fakes. E2E should use local fakes or official sandbox environments, never real financial transactions or uncontrolled production services.                                                                                                                  |
| **Test ownership**          | Test each behavior at the lowest layer that provides sufficient confidence. Do not duplicate every assertion at all six layers.                                                                                                                                                                                 |
| **Async Server Components** | Prefer E2E coverage. Current Next.js guidance notes that Vitest does not fully support testing async Server Components.                                                                                                                                                                                         |
| **Coverage**                | Use coverage as a diagnostic, not a target. High line coverage does not replace route authorization, database constraint, or critical-flow E2E tests.                                                                                                                                                           |
