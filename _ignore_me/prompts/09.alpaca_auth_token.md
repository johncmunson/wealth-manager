### Context and constraints

- This is a Next.js application deployed to Vercel serverless/Fluid Compute.
- There is no guaranteed single long-running process or globally shared memory.
- Alpaca’s recommended flow exchanges a client ID and client secret for a bearer token valid for approximately 15 minutes.
- This is machine-to-machine authentication. It must not introduce browser redirects, consent screens, or other frontend OAuth flows.
- Alpaca credentials and bearer tokens must never reach client components, browser storage, cookies, responses, telemetry, or logs.
- The project currently appears to have no Alpaca integration implementation.
- Use `pnpm`, not npm or Yarn.
- Do not add a database migration during this scoping task.
- Follow the repository’s restricted web-access policy. Only fetch exact known URLs.

11. Should a Broker API request retry once after invalidating a cached token on `401`? Which requests are safe to retry, especially non-idempotent order or funding operations?
12. What logging and observability are useful without leaking credentials?
13. Does `private_key_jwt` materially improve this deployment, or is `client_secret` the appropriate initial choice?

### Alternatives to assess

#### Baseline: per-instance memory cache

Assess a server-only module containing:

- cached token and absolute expiration time;
- an in-flight promise to deduplicate refreshes within an instance;
- on-demand refresh with no background timer;
- an early-refresh safety window;
- expiration checks that remain correct after freeze/thaw;
- `cache: "no-store"` on the token request;
- explicit Node/server-only boundaries.

A cold Vercel instance may fetch a token once, while a warm instance reuses it. Determine whether this is sufficient for the expected initial scale.

#### Shared cache

Assess Redis/KV only if a global token cache is justified. Cover:

- token TTL;
- encryption/access controls;
- distributed locking or single-flight behavior;
- cache outages and fallback behavior;
- operational and dependency costs.

#### PostgreSQL

The project already has PostgreSQL and Drizzle. Assess it as an option, but account for:

- storing a sensitive ephemeral credential;
- encryption requirements;
- row locking/advisory locking;
- unnecessary database traffic;
- schema and migration overhead.

Do not create a schema or migration during this task.
